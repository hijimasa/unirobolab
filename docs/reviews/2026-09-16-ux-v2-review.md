# レビュー: 設計案 v2 (docs/ux-flow.md) とチュートリアル (docs/tutorial.md)

2026-09-16、別エージェント (UX レビュアー役) によるレビューの記録。原文のまま。

## A. チュートリアル (現状 GUI) でライトユーザーがつまずく箇所

- §0 (起動前): tutorial_resources.json を手書きしないと学習ボタンが動かない (learning_port、python パス)。GUI に触る前に最初の壁がある。v2 表 #8 は「押して初めて分かる」までで、手書き設定そのものを無くす視点が無い → 追加。
- 01_start: Task タブに契約が無いのに Goal range ±0.50 のスライダと「Save & train」が押せる状態。案内文自体が「Draft from URDF in 詳細 > Contract」と隠し扉を指す。上部の core の「ROS2 IP / Set IP」バーは ①〜④ では無関係だが常に見える → v2 に無い (追加)。
- 02_draft: 「詳細」を押すとタブ列が詰まって位置がずれる。生成先が servo_demo_redraft.json なのに 03 以降は servo_demo.json で、本文と画面が食い違う。パス欄は右端が切れ、JSON 全文 (contract_version, _notes) がそのまま。
- 03_task: 状態行が「read <フルパス>」。Success 0.05→0.03 で学習時間が 4 倍になることが分からない。
- 04/05_training: 04 は 3D に 1 体しか映らず、05 は 8 体が一列に消失点へ並ぶ。進捗文は日本語、曲線の凡例は英語。「残り 21 分」が上限基準で実際は 12 分 (見積もりの根拠が示されない → 追加)。
- 06_try: Task タブが初期状態 (契約欄空、±0.50) に戻っており、本文の「Task タブと直近の学習結果が使われる」と矛盾 = 再起動で状態消失 (#6) の実例。Try パネルは Entity 名 (ServoDemo_0) を手打ち、Goal はテキスト+無名のスライダ 2 本+「Set goal」と入力経路が 3 つ。
- §4 / 07_check: GUI で完結しない。コンテナに入り 4 コマンドを打つ。「Run check」は sim2sim_command 未設定だと押すまで分からない。本文は「非常停止が効くか確かめる」と言うが画面の 6 項目に非常停止が無い (既定シナリオに含まれていない)。
- 08_deploy: 指令方式が「switch」ボタン、controller 欄は灰色で理由なし。要約は {"ideal_joint": 8.0, ...} の生 dict と英日混在。「Show guide」があるのに本文は「DEPLOY.md を開くボタンがあるとよい」と書く (齟齬)。

## B. 設計案 v2

(1) 解決状況: #1〜#5, #7 はステッパー・①先頭・Camera.rect・④統合・「選ぶ...」・辞書で解決。#6 は「ファイルの有無から復元」だが、①で契約を直した後に古い policy.onnx が残る等の失効 (stale) が定義されておらず不完全。#8 は ③⑤ の前提表示で半分 (設定ファイル手書きは残る)。未解決: ROS2 IP バー、残り時間の根拠、既定シナリオの非常停止、Entity 名 (④で暗黙に解決だが明記なし)。

(2) フェーズ: 順序は概ね妥当だが 1 点致命的: ⑥で名前空間・指令方式を決めると ros-set が契約の ros 節を書き換え、⑤で合格したパッケージと別物を配備する。接続先は ① (ロボット) か ⑤の前に移し、⑥は「作る・手順書・起動コマンド」だけにすべき。②③は「次の一手 → ②へ戻る」の往復が前提なので、③に②のスライダを読み取り専用で残す (or 統合) と行き来が減る。④は任意、⑤は必須とし、④を飛ばして⑤へ行けることを明示。

(3) 画面案:
- ①テキストエディタ主役には反対。#2/#7 (JSON キーを出さない、初手を専門家層に置かない) と v1 原則 5 に自己矛盾する。ライトユーザーが直すのは関節名・トピック・指令方式・固定/移動・安全上限だけなので、右の要約を編集可能な表にして主役にし、JSON エディタは「詳細」へ。3D の関節ハイライトは要約表の行選択と結ぶ。編集ごとの unirobolab show 呼び出しはデバウンス必須。
- ②: 学習時間の目安は良い。目安の根拠 (体数・許容誤差) を 1 行添える。
- ③: 2 回目以降の run の扱い (runs/ が複数になる、上書き確認) が無い。「次の一手」は提案値を入れた状態で②へ飛ぶ。
- ⑤: 「チェックを実行」1 ボタンの裏に gen → colcon build → bringup (第 2 のシミュレータ起動) → sim2sim があり数分かかる。段階ごとの進捗、docker の有無、GUI 側プレイヤーと bringup のプレイヤーのポート衝突 (ROS-TCP 10000 / learning_port) の設計が無い。理想は GUI のシミュレータ自身を被検体にする。既定シナリオに非常停止を入れる。
- ⑥: 「⑤で検証した方策/契約と同一」の印を出す。

(4) フェーズ別「詳細」は良い。プロジェクト単位も良いが、unirobolab.project.json に各成果物の由来 (契約ハッシュ・時刻) を持ち、上流を変えたら下流を「要やり直し」に落とす状態機械が要る。解放条件は妥当だが、⑥の入力が⑤の前提を壊す。

(5) LabPanel は既に 1071 行のコード生成 uGUI。6 画面+ステッパーを同じ手法で書くと肥大するので、レイアウト用の小さなヘルパか UI Toolkit を検討 (TMP の CJK 動的フォント登録は uGUI 前提なので移行コストあり)。Camera.rect は ScreenPointToRay が rect を考慮するので Pick in 3D は動くが、パネル上のクリック除外と、rect 外の未描画領域をパネル背景で覆うこと。子プロセス: 1 秒ごとの train-status、編集ごとの show は Python 起動コストが積む。live 実行器と同じく常駐プロセス (stdin/stdout の JSON 行) に寄せる。

## C. 優先順位

概ね賛成だが変更提案: 共通骨格+プロジェクト+ファイル選択 (安い、#1#4#5#6 を一掃) → ②③ (学習時間の目安は最大の落とし穴で安い) → ①は最小版 (選ぶ→草案→要約+3D、エディタは詳細) → 接続先の①移動と⑤のコンテナ実行 (GUI で通らない唯一の穴) → ④ (PolicyPanel 移植で安い) → ⑥ → ① の編集表。① のフル実装は最も高く効果が中なので後ろへ。

## D. 総合評価: 3 / 5

方向は正しいが、実装前に直すべき点:
1. ⑥ の接続先入力が⑤の検証を無効にする順序矛盾 → 接続先を ① へ。
2. ① のテキストエディタ主役を撤回し、編集可能な要約表を主役、JSON は詳細へ。
3. ⑤ の実行モデル (チェーン、第 2 シミュレータとポート、進捗、docker 前提、非常停止シナリオ) を具体化。
4. プロジェクトの失効ルール (上流変更→下流やり直し) と複数 run の扱い。
5. 起動前の設定手書きを無くす (既定 learning_port、python の自動検出、初回セットアップ画面) と CLI 呼び出しの常駐化。
